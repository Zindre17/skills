# Refinement: /linus skill — 2026-09-28

## Brief (verbatim)

> I want to create a skill for guiding code writing. I want to call it "/linus", and it should be called automatically when writing code. What the skill should do is to implement the given feature 3 times. Do it the way it first comes to mind. Then discard everything and do it again with the knowledge about what caused friction the first time. Then discard it once more - because it often turns out the rewrite oversimplified something the first attempt actually did correct - which causes another kind of friction. So the third time is the charm. It can use the wisdom gained in both attempts and create the smoothest path for this feature.

## Round 1

### Q1 Scope
**Question:** "Called automatically when writing code" — but three full passes triples time and tokens. A typo fix or a one-line bug fix done three times is pure cost. Where should /linus switch on?

- **Features, not edits (Recommended)** — New behaviour or multi-file change; skip small fixes and tweaks.
  Preview: Triggers: "add X", "implement Y", "build Z", any change touching several files or introducing a new module/API. Skips: typo, rename, one-line bug fix, config tweak, formatting. WHY: The friction the method hunts for only shows up when there is a design to get wrong. A one-liner has no shape to discover. Cost: the boundary is a judgement call the model makes, so it will sometimes misjudge a medium change.
- **Every code change** — Always three attempts, however small.
  Preview: Every Edit/Write to source code goes through the loop. WHY NOT: most small changes produce three identical attempts; 3x cost per typo; you'll turn it off.
- **Only when invoked** — Never automatic; you type /linus when you want it.
  Preview: disable-model-invocation. WHY NOT: contradicts "called automatically". Right if auto-triggering fires too often.

**Answer:** Features, not edits (Recommended).

### Q2 Runner
**Question:** Discarding only works if attempt 2 can't lean on attempt 1's code. The same agent in one context remembers everything it wrote; fresh sub-agents genuinely start over but lose tacit knowledge. Who writes each attempt?

- **Fresh sub-agent each (Recommended)** — Each attempt in its own worktree; main agent orchestrates.
  Preview: fresh context can't anchor on old code, so the rewrite is real. Costs: needs git; anything not in the notes is lost — the notes are the whole product.
- **Main agent, reset between** — One context; git reset/stash between attempts.
  Preview: cheapest, keeps tacit knowledge, but old code sits in context: attempt 2 tends to be attempt 1 with edits.
- **Hybrid: 1-2 fresh, 3 main** — Sub-agents explore; main agent writes the final.
  Preview: attempts 1 and 2 in throwaway worktrees; main agent, having read both diffs and friction logs, writes attempt 3. Trade-off: matches "use wisdom from both", but main context gets heavy, and the final author never felt the friction first-hand.

**Answer:** Hybrid: 1-2 fresh, 3 main.
**User note (verbatim):** "My intuition is telling me to go with this. But I am interested to hear why you say that the final author never felt the friction first hand. Wouldn't that be the case for 3 subagents too? I guess the only way to avoid that is to do all on the main agent."

### Q3 Done bar
**Question:** Friction you only feel when code runs (tests, edge cases, wiring) is missed if an attempt is thrown away half-written. But driving every attempt to green multiplies the cost. How finished must attempts 1 and 2 be?

- **Working, tests pass (Recommended)** — Each attempt compiles and passes its own tests. Preview: the "rewrite oversimplified what attempt 1 got right" failure is usually an edge case only running code reveals. Most expensive; falls back to "compiles" with no test setup.
- **Compiles, untested** — catches shape friction cheaply, misses behavioural friction.
- **Timeboxed sketch** — cheapest; friction hides in the last 20%.

**Answer:** Working, tests pass (Recommended).

### Q4 Carry
**Question:** Your brief says attempt 3 uses "the wisdom of both". That wisdom has to travel as something. Notes alone may lose the detail of what attempt 1 got right; old code invites copy-paste. What crosses between attempts?

- **Friction log + read-only diffs (Recommended)** — Written log is primary; diffs available to consult, not copy.
- **Friction log only** — Pure notes; prior code is deleted and unseen.
- **Log; attempt 3 sees all** — Attempt 2 gets notes only; attempt 3 gets everything. Risk: attempt 3 becomes a merge of 1 and 2 rather than a clean third design.

**Answer:** Log; attempt 3 sees all.
**User note (verbatim):** "What if we choose this, but are very explicit about extracting the design before staring to write code? Maybe that would avoid attempt 3 becoming a merge? I have a feeling your recommended answer will guide subsequent attempts too much if the entire diff is sent. And I also feel like the final attempt should have everything available.."

**Resulting decision:** Attempt 2 sees friction log 1 only. Attempt 3 sees both logs and both diffs, but must first write a **Design brief** before any code (term added to CONTEXT.md).

## Round 2

### Q5 Log owner
**Question:** You're right: three sub-agents have the same gap, and only all-main avoids it (at the cost of attempt 2 anchoring on code it remembers). With hybrid, the fix is who writes the Friction log. Who writes it?

- **Sub-agent, main reviews (Recommended)** — Author writes it live; main agent audits against diff/tests. Preview: friction felt first-hand once, by the author, captured then; main agent's audit catches self-report blind spots (e.g. a hack not flagged as a hack).
- **Sub-agent only** — cheaper; agents under-report their own workarounds.
- **Main agent from artifacts** — loses first-hand experience; dead ends leave no trace in a final diff.

**Answer:** Sub-agent, main reviews (Recommended).

### Q6 Brief 2
**Question:** The Design brief step is settled for attempt 3. Should attempt 2 also write a brief from friction log 1 before coding? Attempt 1 stays gut-first by definition.

- **Yes, briefs for 2 and 3 (Recommended)** — Without a brief, attempt 2 patches log 1's complaints one by one instead of rethinking; brief 2 also lets attempt 3 compare intent vs result.
- **Only attempt 3** — faster; risk attempt 2 = attempt 1 minus complaints.

**Answer:** Yes, briefs for 2 and 3 (Recommended).

### Q7 Gate

- **No gate, brief in report (Recommended)** — Runs through; you see the brief in the final report.
- **Gate before attempt 3** — Pause; you approve or edit the brief first.

**Answer:** No gate, brief in report.
**User note (verbatim):** "No gate by default. Maybe we could create a different skill that gates by default, but otherwise identical. Or give gate or not as paramter to the skill."

### Q16 Stuck
**Question:** A throwaway attempt may never get tests green -- a wrong design can be the reason. Endless retries burn tokens; giving up early wastes the lesson. What happens when a sub-agent is stuck?
